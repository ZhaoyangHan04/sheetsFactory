# First native development for the scoped eight-business pair

`scripts/prepare_heterogeneous_native_development.py` prepares one modeling or
debugging task from a genuine completed native view validation. Preparation and
`validate` read existing evidence and write the standard export. Only the
explicit `run-development` command launches one model attempt.

The admission boundary is the new SHA-bound
`validate_heterogeneous_review_task_pair_v2.py` completed validator. Every prepare
and revalidation calls that real cold validator. A persisted `passed` flag is
insufficient. Only corrected native version 2 is accepted; the retained failed
version 1 and old linear source, material, and validator envelopes cannot enter
this entry point. The native source presentation is an XLSX reference, with its
original source lineage retained separately.

Each mode must retain exactly seven successful owned calculation calls, all
766 independent financial scope values, the entire changed-value set, all five
controls, both full typed stability comparisons, actual resource evidence and
cleanup, six approved presentation text corrections and their two exact direct
text-alias caches, and unchanged original
source evidence. A completed material may change only its calculated public
input, calculated goal, actual D, raw-input ancestry field, and completion flag.
The export uses the exact recalculated input1 and goal1 bytes. The development
gate independently recomputes their full changed-value set before export.

The resource export contains exactly the standard 17 files. Its private thread
cap audit remains outside that export. The environment and verifier retain the
pinned image, 2 CPU, 32 GiB and `MAX_CONCURRENCY=2` contract. The public instruction
and input and private reference are bound to their genuine actual task bytes.

The model and transport are frozen before the first call: native `gpt-6.1-sol`,
`xhigh`, provider stream retries 8, and zero outer infrastructure retries. The
unchanged clock v3 policy counts the sum of tool durations strictly below 1800
seconds and excludes model time. The 14400-second elapsed limit is a separate
operational guard. Missing timing or infrastructure failure does not become a
scored model zero or authorize a retry.

Both `outputs/difficulty` and `outputs/research` are searched for every prior
selection. The exact known zero-model composite preparation schema is retained
as preparation history and is excluded from model-selection dispatch. Unknown
or corrupt history fails closed. Existing frozen history must remain present
and unchanged; unrelated later selections are allowed and the complete current
history is bound at launch under the global reservation lock.

Material identity covers complete logical input definitions and values, goal
values, public instruction, mode, and full scope. A second cross-snapshot
reservation uses the mode and core content identity, independent of paths, task
names, family labels, scope naming and ZIP packaging. A failed launch keeps its
reservation permanently. Each snapshot also has its own launcher lock. Different
modeling and debugging materials can register in turn and then run concurrently.

For example, prepare both snapshots before starting either model:

```bash
.venv312/bin/python scripts/prepare_heterogeneous_native_development.py prepare \
  --validation-manifest /absolute/FM/actual_terminal.json \
  --output /absolute/fresh/FM_snapshot
.venv312/bin/python scripts/prepare_heterogeneous_native_development.py prepare \
  --validation-manifest /absolute/DBG/actual_terminal.json \
  --output /absolute/fresh/DBG_snapshot
```

`run-development --prepared SNAPSHOT --output FRESH_EVALUATION` spends that
material's first attempt. There are no model, effort, confirmation, resume, or
retry overrides.
